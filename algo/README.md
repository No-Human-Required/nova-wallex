# الگوریتمیک (Algorithmic) — پلتفرم ساخت و اجرای ربات معامله‌گر

برنامه‌ای جدا از موتور حساب Nova در همین مخزن: پروسه، فضای پایگاه‌داده و کانتینر جدا. کاربر با کد پیامکی وارد می‌شود، ربات می‌سازد، بک‌تست می‌گیرد، آزمایشی (کاغذی) اجرا می‌کند و پس از تأیید ادمین روی حساب صرافی خودش (فعلاً والکس) اجرای واقعی دارد. بک‌آفیس همهٔ تنظیمات، کاربران، پلن‌ها، پرداخت‌ها و تأییدها را مدیریت می‌کند.

## اجزا

| بخش | فایل | کار |
| --- | --- | --- |
| وب | `algo/main.py`، `algo/static/` | سایت عمومی، پنل کاربر با همان UI نوا، بک‌آفیس، API |
| داشبورد | `algo/views.py` | داده‌های هر ربات به شکل صفحه‌های نوا: اجرای زنده، نحوهٔ تصمیم‌گیری، ژورنال، تصمیم‌های AI، تست سایه |
| استودیو | `algo/studio.py` | استودیوی استراتژی عامل‌محور نوا برای هر کاربر؛ کلید LLM پلتفرم و سهمیهٔ ماهانه؛ استراتژی تأییدشده در سازندهٔ ربات |
| ورود | `algo/auth.py`، `algo/sms.py` | کد ۶ رقمی با پترن IPPanel (کد `fuspysk44m9yajp`، متغیر `OTP`)، ۲ دقیقه اعتبار، ۵ تلاش، محدودیت هر شماره و هر IP |
| پرداخت | `algo/payments.py` | زرین‌پال v4؛ sandbox یا واقعی از بک‌آفیس؛ تمدید پلن فقط یک بار برای هر پرداخت تأییدشده |
| ربات | `algo/bots.py`، `algo/exchanges.py` | پارامترهای همان آزمایشگاه بک‌تست + پروفایل ریسک + فیلتر AI؛ والکس فعال، نوبیتکس «به‌زودی» |
| اجرا | `algo/executor.py`، `algo/runner.py` | یک مسیر برای آزمایشی و واقعی؛ هر ۳۰ ثانیه خروج‌ها، در بسته‌شدن هر کندل ورودها |
| AI | `algo/ai.py` | همان `AdaptiveAI` نوا با کلید پلتفرم و سهمیهٔ ماهانهٔ هر کاربر |

## پنل کاربر (همان UI نوا)

پنل کاربر روی همان فایل‌های نوا ساخته شده است: `static/nova.css`، `static/js/charts.js` و `static/js/fx.js` مستقیم از `/nova/` بارگذاری می‌شوند و صفحه‌های نوا در `algo/static/js/` برای «ربات انتخاب‌شده» بازنویسی شده‌اند (`core.js` مسیرهای `/api/public/...` را به `/api/u/bots/{id}/...` می‌برد).

| صفحه | محتوا |
| --- | --- |
| داشبورد ربات | ارزش لحظه‌ای، منحنی ارزش با نقاط خرید/فروش، اسکنر رادار و رژیم، هر موقعیت با نمودار دقیقه‌ای و خطوط ورود/حد ضرر/سه TP، آخرین تصمیم AI، نامزدها، معاملات و رویدادها، دکمه‌های شروع/توقف/فروش |
| نحوهٔ تصمیم‌گیری | جریان متحرک داده تا سفارش، اسکرینر با پخش تاریخچه برای هر کندل، اندازه‌گذاری با سقف تعیین‌کننده، پرتفو و وزن‌ها، نردبان خروج، تست سایه |
| ژورنال / تصمیم‌های AI | همهٔ سفارش‌ها و معاملات رفت‌وبرگشت با دلیل، خروجی CSV/JSON، هر تصمیم مدل با استدلال و توکن |
| استراتژی‌ها / بازار زنده | کاتالوگ و رژیم‌ها (شامل استراتژی‌های استودیوی کاربر)، شواهد بک‌تست، نقشهٔ حرارتی و نمودار هر بازار |
| استودیوی استراتژی | گفت‌وگو با عامل، پیش‌نویس، بک‌تست ۷روزه روی کندل‌های والکس، بهینه‌سازی، آزمون کامل، تأیید |
| بک‌تست و پژوهش | آزمایشگاه بک‌تست نوا (هر تایم‌فریم و بازه) با امکان بارگذاری تنظیمات هر ربات |

ربات در بسته‌شدن هر کندل اسکن (مرحلهٔ هر نماد)، تصمیم AI و تخصیص (همهٔ سقف‌ها و سقف تعیین‌کننده) را در `bot_scans`، `bot_decisions` و `bot_events` ثبت می‌کند؛ ۵۰۰ کندل آخر نگه داشته می‌شود. ادمین می‌تواند داشبورد هر ربات را فقط‌خواندنی ببیند.

## معاملات تعهدی (اهرمی) والکس

ربات می‌تواند به‌جای اسپات در «معامله تعهدی» والکس کار کند (`algo/margin.py`، طبق `docs/wallex/margin-*.md`): لانگ، شورت یا هر دو، با نسبت اعتبار (اهرم) انتخابی تا سقفی که ادمین در «بک‌آفیس ← تنظیمات ← معاملات تعهدی» تعیین می‌کند.

- **سیگنال شورت:** همان استراتژی‌ها روی قیمت معکوس (۱/P) اجرا می‌شوند؛ صعود در آن سری یعنی نزول قیمت واقعی. نردبان TP، حد ضرر شناور و پله‌ای و خروج برگشت روند برای شورت هم همان است.
- **ایمنی:** ورودی که حد ضررش نزدیک یا بعد از قیمت لیکویید باشد باز نمی‌شود (روی ربات واقعی با «پیش‌نمایش» خود والکس)؛ حد ضرر و حد سود از اولین درخواست روی صرافی ثبت می‌شوند و با رسیدن به هر TP حد ضرر صرافی هم بالا می‌آید؛ موقعیتی که صرافی بسته (حد ضرر، حد سود، لیکویید، پایان ۲۱ روز) با سود و زیان خود صرافی ثبت می‌شود.
- **پاسخ نامعلوم:** API باز کردن موقعیت شناسهٔ سفارش مشتری ندارد؛ درخواست بی‌پاسخ فقط با خواندن موقعیت‌ها روشن می‌شود (دقیقاً یک موقعیت تازه در همان بازار و سمت)؛ هرگز دوباره ارسال نمی‌شود؛ اگر دو موقعیت ناشناخته باشد ربات برای بررسی مسدود می‌شود.
- **کلیدهای توقف:** «معاملات تعهدی واقعی» (پیش‌فرض خاموش) و «معامله با پول واقعی»؛ خاموش بودن هرکدام یعنی هیچ موقعیت تعهدی تازه‌ای باز نمی‌شود و ربات‌ها فقط خروج را مدیریت می‌کنند.
- **بک‌تست:** آزمایشگاه نوع بازار، اهرم و سمت را می‌گیرد؛ کارمزد معامله، کارمزد فعال‌سازی و تمدید ۴ساعته و لیکویید شبیه‌سازی می‌شوند (کارمزدهای تعهدی فرض‌اند و قابل تغییر).

## اعلان‌ها در ربات بله و پایش حساب

- **ربات بله** (`algo/notify.py`، API سازگار با تلگرام: `https://tapi.bale.ai/bot<token>/...`): در بله با @botfather یک ربات بسازید و توکن و نام کاربری آن را در «بک‌آفیس ← تنظیمات ← اعلان‌ها (ربات بله)» وارد و فعال کنید. کاربر در «حساب من» کد ۶ رقمی می‌گیرد و برای ربات می‌فرستد تا حسابش وصل شود.
- پیام‌ها: ورود و خروج هر معامله (قابل بی‌صدا شدن)، رسیدن به TP، شروع و پایان بازهٔ زمانی، تمام شدن سهمیهٔ AI، و هشدارهای مهم که همیشه ارسال می‌شوند: مسدود شدن ربات، ناهمخوانی موجودی، لیکویید شدن، رد یا تأیید اجرای واقعی. ادمین‌های وصل‌شده هشدارهای مهم و درخواست‌های اجرای واقعی را هم می‌گیرند.
- دستورهای ربات: `/status` وضعیت ربات‌ها، `/mute` و `/unmute`، `/unlink`.
- پیام‌ها اول در جدول `notifications` ذخیره و توسط پروسهٔ runner با تلاش دوباره ارسال می‌شوند؛ فقط runner صندوق ربات را می‌خواند (یک مصرف‌کننده برای هر توکن).
- **تطبیق موجودی:** هر ۱۰ دقیقه موجودی صرافیِ هر کلید با مجموع دارایی‌های ربات‌های واقعی اسپاتِ همان کلید مقایسه می‌شود؛ اگر کمتر باشد (معاملهٔ دستی، انتقال)، ورود جدید آن ربات‌ها متوقف می‌شود و هشدار می‌رود؛ چیزی خودکار فروخته نمی‌شود.
- **محدودیت درخواست والکس:** همهٔ ربات‌ها یک کش و یک سقف مشترک (۸ درخواست در ثانیه) برای دفتر سفارش دارند و پس از پاسخ 429 ده ثانیه صبر می‌کنند.

## پایداری اجرا (۱٫۵)

- **اجرای موازی:** ربات‌ها در چند رشته (`ALGO_RUNNER_WORKERS`، پیش‌فرض ۶) اجرا می‌شوند؛ درخواست کند AI یا صرافی برای یک ربات، حد ضرر ربات‌های دیگر را عقب نمی‌اندازد. هیچ رباتی هم‌زمان دو چرخه ندارد.
- **نگهبان اجراکننده:** runner هر چند ثانیه ضربان ثبت می‌کند. اگر بیش از ۳ دقیقه ضربان نباشد، supervisor آن را ری‌استارت می‌کند و وب‌سرور مستقیم به ادمین‌ها در بله خبر می‌دهد (و پس از برگشت هم). «نمای کلی» بک‌آفیس وضعیت اجراکننده را نشان می‌دهد.
- **خطای پیوسته:** رباتی که ۱۵ دقیقه چرخهٔ موفق نداشته باشد یک بار به کاربر و ادمین گزارش می‌شود.
- **اجرای آزمایشی واقع‌بینانه‌تر:** سفارش آزمایشی روی سطوح دفتر سفارش (تا ۲۵ سطح) و تا قیمت لیمیت پر می‌شود؛ سفارش بزرگ ممکن است نیمه‌پر یا با میانگین بدتر پر شود.
- **بله:** `/pause` ورود جدید همهٔ ربات‌های کاربر را فوراً متوقف می‌کند (خروج‌ها مدیریت می‌شوند) و `/resume` برمی‌گرداند؛ گزارش روزانه ساعت ۲۳:۳۰ (`/daily` برای روشن/خاموش).
- **پاک‌سازی:** پیام‌های ارسال‌شده و لاگ ورود پس از ۳۰ روز، نشست‌ها و کدهای منقضی، و رویدادهای غیرمعاملاتی پس از ۱۸۰ روز حذف می‌شوند.

## بازهٔ زمانی اجرای ربات

هر ربات «شروع» و «پایان» دارد (هر دو اختیاری): شروع خالی یعنی همان لحظهٔ زدن «شروع»، پایان خالی یعنی نامحدود. اگر شروع در آینده باشد ربات «زمان‌بندی‌شده» می‌ماند و خودکار روشن می‌شود. در پایان بازه ورود جدید انجام نمی‌شود و یکی از دو رفتار اجرا می‌شود: «فروش و توقف» (همهٔ موقعیت‌ها با قیمت بازار فروخته می‌شوند) یا «فقط مدیریت خروج» (موقعیت‌ها با حد ضرر و TP بسته می‌شوند، سپس توقف). بازه را می‌توان هر زمان از داشبورد («تغییر بازه») عوض کرد؛ این تغییر تأیید اجرای واقعی را برنمی‌دارد. شمارش معکوس بالای داشبورد زمان شروع یا پایان را نشان می‌دهد.

## قواعد ایمنی اجرای واقعی

- اجرای واقعی فقط با: کلید API تأییدشده (فقط خواندنی بررسی می‌شود)، پلنی که ربات واقعی دارد، و **تأیید ادمین**. هر تغییر تنظیمات تأیید را برمی‌دارد.
- هر سفارش پیش از ارسال با شناسهٔ یکتا ثبت می‌شود؛ پاسخ نامعلوم فقط با GET روشن می‌شود و تا وقتی سفارشی نامعلوم است، ربات سفارش تازه نمی‌فرستد. اگر ۳۰ دقیقه نامعلوم بماند، ربات مسدود می‌شود تا ادمین بررسی کند.
- ربات فقط از سرمایهٔ اختصاصی خودش خرج می‌کند و هرگز بیش از موجودی آزاد تومان حساب؛ فقط دارایی‌ای را می‌فروشد که خودش خریده است.
- فروش‌ها لیمیت قابل‌اجرا با سقف ۲٪ زیر بهترین خرید، خریدها با سقف ۰٫۳٪ بالای بهترین فروش؛ باقی‌ماندهٔ پرنشده پس از ۶۰ ثانیه لغو می‌شود.
- اجرای واقعی فعلاً فقط بازارهای تومانی را معامله می‌کند.
- دو کلید توقف سراسری در بک‌آفیس: «معامله با پول واقعی» (هیچ سفارش واقعی) و «ورودهای جدید» (فقط مدیریت خروج).

## استقرار روی رانفلر (اپ جدا از Nova)

1. `python scripts/package_algorithmic.py` فایل `dist/algorithmic-runflare-v1.5.0.zip` را می‌سازد (Dockerfile در ریشه).
2. یک اپ جدید در رانفلر با یک PostgreSQL (می‌تواند همان سرور Nova باشد؛ فضای `algorithmic` جداست) و یک دیسک برای `/data`.
3. متغیرهای محیطی:

| متغیر | مقدار |
| --- | --- |
| `ALGO_ORIGIN` | آدرس عمومی، مثلاً `https://algorithmic-trade.ir` |
| `ALGO_VAULT_KEY` | کلید Fernet (`python -c "from cryptography.fernet import Fernet;print(Fernet.generate_key().decode())"`)؛ گم شود، کلیدهای ذخیره‌شده قابل بازگشایی نیستند |
| `ALGO_ADMIN_PHONES` | شماره‌های ادمین اولیه، جدا با کاما |
| `SW_DATABASE_URL` | آدرس PostgreSQL |
| `SW_DB_NAMESPACE` | `algorithmic` (پیش‌فرض Dockerfile) |
| `PORT` | پورتی که در رانفلر انتخاب کرده‌اید، مثلاً `8000` |
| `ALGO_SMS_API_KEY` | کلید API پنل IPPanel (برای اولین ورود ادمین لازم است) |
| `ALGO_SMS_SENDER` | شمارهٔ فرستنده، مثلاً `+983000505` |

هر تنظیم بک‌آفیس را می‌توان با متغیر محیطی `ALGO_` + نام تنظیم با حروف بزرگ و `_` به‌جای نقطه هم داد (مثلاً `sms.pattern_code` ← `ALGO_SMS_PATTERN_CODE`). مقداری که در بک‌آفیس ذخیره شود بر متغیر محیطی مقدم است.

4. با شمارهٔ ادمین وارد شوید؛ در «بک‌آفیس ← تنظیمات»: کلید API و شمارهٔ فرستندهٔ IPPanel، مرچنت زرین‌پال (و خاموش کردن sandbox هنگام واقعی شدن)، کلید LLM پلتفرم. «ارسال پیامک آزمایشی» را بزنید.
5. پلن‌ها را در «بک‌آفیس ← پلن‌ها» تنظیم کنید (پیش‌فرض: رایگان، حرفه‌ای، ویژه).

اجرای محلی: `ALGO_ENV=development ALGO_VAULT_KEY=... ALGO_ADMIN_PHONES=0912... PORT=8090 python -m algo.serve` (در حالت توسعه اگر پیامک تنظیم نباشد کد روی صفحه نشان داده می‌شود) و در پنجرهٔ دیگر `python -m algo.runner`.

## آزمون‌ها

`python -m unittest tests.test_algorithmic` — داشبورد نوا برای هر ربات و دسترسی‌ها، استودیو تا استفاده در ربات و آزمایشگاه، ورود و محدودیت‌ها، ادمین و CSRF، رمزنگاری تنظیمات، شکل درخواست IPPanel، پرداخت یک‌باره، چرخهٔ ربات و تأیید، اجرای آزمایشی، سفارش نامعلوم، نردبان TP، کلیدهای توقف و مجوز نوشتن.
